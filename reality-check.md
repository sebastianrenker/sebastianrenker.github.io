# RENKER Reality Check

Stand: 2026-08-11. Basis: direktes Auschecken und Ausführen von `rencora`, `renkervault`, `continuum`, `renker-core-authz` (Stand `main`, jeweils aktuellster Commit zum Prüfzeitpunkt). `renker-core` selbst ist ein **privates** Repository und war für diese Prüfung nicht einsehbar — siehe Hinweis am Ende.

Methodik: Für jeden Claim wurde entweder Code gelesen, eine Testsuite tatsächlich ausgeführt, ein CI-Workflow inspiziert, oder ein Dokument (SECURITY.md, ROADMAP.md, Wiki) als Primärquelle zitiert. Kein Claim in diesem Dokument beruht auf bloßer Ankündigung.

Statuswerte: **REAL** (im Code vorhanden und verifiziert lauffähig) · **PARTIAL** (Kernidee im Code vorhanden, aber eingeschränkt/unvollständig/nicht extern geprüft) · **PLANNED** (in Roadmap/Doku beschrieben, im Code als Interface oder TODO angelegt, nicht funktional) · **UNVERIFIABLE** (Repo nicht zugänglich für diese Prüfung).

## Wichtigste plattformweite Befunde

1. **Kein Repository behauptet mehr, als es hält.** Alle vier eingesehenen READMEs/SECURITY.md enthalten bereits eigene "ehrliche Grenzen"-Abschnitte. Das ist ein echter Marketing-Vorteil (Glaubwürdigkeit), sollte aber genauso in neuem Marketingmaterial fortgeführt werden statt verwässert.
2. **renker-core-authz ist der am besten belegte Baustein** der gesamten Plattform: 88 Tests, CI mit Format/Lint/Typecheck/Test/Build/Dependency-Audit, präzise benannte Grenzen. Er sollte das Zugpferd für alle "das ist kein Marketing-Versprechen, das ist Code"-Aussagen sein.
3. **Größte Lücke: CI-Automatisierung fehlt bei rencora (Tests nicht in CI) und komplett bei renkervault (kein `.github/workflows`).** Vorhandene Tests sind real, laufen aber nicht automatisch bei jedem Push — das darf nicht als "continuously tested" beworben werden, bevor es stimmt.
4. **renker-core ist privat und für externe Prüfung/Marketing-Verifikation nicht zugänglich.** Jede Aussage über renker-core selbst (statt über die öffentlich sichtbaren Konsumenten) ist aktuell unbelegbar von außen. Empfehlung: entweder (a) renker-core öffentlich machen, mindestens die Interface-/Doku-Ebene, oder (b) in der gesamten Außenkommunikation konsequent auf `renker-core-authz` als den öffentlich verifizierbaren Kern verweisen und renker-core nur als "privates Repository, derzeit die interne Referenzimplementierung" erwähnen.
5. **Continuum ist der ehrlichste, aber auch am wenigsten "fertige" Baustein.** Simulierte Daten, keine Hardware, Phase 0 von 4. Die Evidenzkategorisierung (`EXPERIMENTAL`/`PREDICTED`/`LITERATURE`) ist ein starkes, echtes Alleinstellungsmerkmal und sollte technisch genau so benannt werden — nicht als generisches "PROPOSED → TESTED → REPRODUCED → VALIDATED" (diese Pipeline existiert im Code nicht in dieser Form).
6. **Rencora ist am weitesten von seiner Zielpositionierung entfernt.** Die Wiki-Positionierung ("Agent Runtime mit Capability Security") beschreibt die Zielarchitektur; der heutige Code ist in erster Linie ein funktionsreicher Desktop-Assistent mit einer *optionalen* Capability-Guard-Integration. Marketing sollte das als "on the way to" formulieren, nicht als Ist-Zustand.
